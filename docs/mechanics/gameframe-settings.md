# Gameframe settings: what the server owns (rev 242)

Scope: the "All settings" interface (`settings`, 134), the cs2-built toggles of other side panels (spell filters, ...),
the chatbox filter buttons and the display layout dropdown. Method: the client scripts (decompiled `.rs2asm`),
cache structs/enums, and the real rev 242 client (RuneLite 1.13.6) against our server with every incoming packet
logged (2026-11-07). Rules for the controls the server does handle are in `gameframe-buttons.md`.

| # | Finding | Source |
|---|---|---|
| G1 | The All settings list is built entirely by client script 3840 (rows from enums 422/423 -> struct lists -> structs; struct param 1077 is the setting id, 1078 the row type, 1086 title, 1096 description). Setting ids map to varbits in client script 6716 (read) and 3965 (write: `get_varbit x; sub; set_varbit x`, i.e. the client sets its own copy of the varbit). The category tabs (`settings` 134:24) and every toggle, slider, dropdown and input are cs2-created children whose ops (`cc_setop`) run client scripts only. | `scripts/3840,3841,3846,3965,6716.rs2asm`; cache enums 422/423, structs |
| G2 | **Nothing is sent to the server when a setting in 134 changes.** Logged packets for category switches, toggles, dropdown opens, slider clicks and "Reset" were none; only the Close button (`134:4`) sends IF_BUTTON op 1 (the engine closes the modal). | rev 242 client, packet log |
| G3 | Dynamic children only send IF_BUTTON when the server enabled their events (IF_SETEVENTS), like the XP drops dropdown rows (O2). With events enabled on `134:3..31` the client sends `134:24 sub=<category>` for tabs (0 Activities, 1 Audio, 2 Chat, 3 Controls, ...), `134:20 sub=<row>` for toggle and dropdown rows (1-based row in the category) and `134:19 sub=<26 + 25 x slider row>` for slider tracks. The slider packet carries no value and the toggle packet no setting id or new value, so the server could not store the result even with events on. We do not enable them. | rev 242 client with a temporary events-on experiment (reverted) |
| G4 | Consequence: settings changed in 134 (and in the cs2-built panels below) live in the client only. They are not saved by the server and are not restored by `VarpReset` at login. The side-panel controls with static components that the server enables itself (run, accept aid, PK skull prevention, attack priority, volume icons/sliders, zoom toggle) are handled and saved as varps (`gameframe-buttons.md` S3..S6). **OPEN-G4:** how the real game persists All settings across sessions (no packet carries them; a client-side preference store is the only explanation left). | G2, G3 |
| G5 | Spell filters (the "Filters" panel of the spellbook, 218): the checkboxes are cs2-built `Change` rows that send nothing (checked: clicking changed nothing and logged no packet). Client-local, like G1. | rev 242 client |
| G6 | Chatbox filter buttons (`chatbox` 162:7 game, 11 public, 15 private, 19 channel, 23 clan, 27 trade): a click sends IF_BUTTON (ops 1..8 per the cache action lists), the client switches/filters locally, and the client sends `SET_CHATFILTERSETTINGS` (public, private, trade filter) at login and on change. The packet is protocol-api `ClientCommand.ChatFilters`: the engine saves the three values (`saved` key `chat.filters`) and sends them back (CHAT_FILTER_SETTINGS + its private-chat packet) at once and at login. **OPEN-G6b:** the private filter's effect on how others see this player's online status is not applied. Game/channel/clan filter buttons are client-only. | `SetChatFilterSettings.kt`, `Network.kt` listener list, rev 242 client |
| G7 | Report buttons (`chatbox` 162:31 op 2 "Report abuse", op 4 "Report game bug") send IF_BUTTON; no server handler. **OPEN-G7:** opening `reportabuse` (875) needs its client script arguments; no reference. | cache interface 162, packet log |
| G8 | "Game client layout" dropdown (`settings_side:display_dynamic_setting_1_buttons` rows 1..3 = fixed 548, resizable classic 161, resizable modern 164). Content names every destination by its fixed-mode `toplevel` component; the engine keeps the player's toplevel and redirects destinations through the cache's pane-redirect enums (1129 maps 161's components to 548, 1130 to 161, 1131 to 164). A change between fixed and resizable first sends client script 3998 (mode 0/1/2), then after 2 ticks (1 between the two resizable ones), on a soft timer, IF_OPENTOP the new toplevel and IF_MOVESUB every open sub-interface (modal included), set `resizable_stone_arrangement` (4607; 1 for modern), save the choice and reopen the orbs. At login the saved layout is used when the login block's window mode matches it (fixed window: 548; resizable: the saved resizable one, else 161). Verified in the client: all three layouts and back. **OPEN-G8b:** after resizable classic -> modern the dropdown still reads "Resizable - Classic layout" until the next switch (RS Mod also skips 3998 there; it resyncs varps `chat_filter_assist` / `settings_tracking`, effect unknown). | RS Mod `DisplaySettingsScript`, `GameframeScript` (`queueGameframeMove`, `moveGameframe`, `openLoginGameframe`); `cache-dump config enum 1129/1130/1131` |
| G9 | Skill guide: op 2 of a skill in the Skills tab (`stats` 320:1..24; the client's hotkey script 7780 triggers the same op) opens `skill_guide_v2` (860) in `toplevel:mainmodal` (script 1902 finds it through the pane-redirect key 161:16 = 548:41) and runs init script 1902 (guide id, tab 0, 0, 0). Guide ids are enum 108's keys (1 Attack, 2 Strength, 3 Ranged, 4 Magic, 5 Defence, 6 Hitpoints, 7 Prayer, ... 24 Sailing). The guide draws itself and keeps its own state (varcs 1168..1173); its tabs are client-side. `skill_guide_v2:close` op 1 closes it. Verified in the client (Attack: Overview, Weapons, Close). **OPEN-G9:** the setting `option_skill_guide` (varbit 15321) probably selects the legacy guide (214); the legacy guide is not implemented. | CS 1902 / 1904 / 7780, enum 108, `cache-dump interface 860` |
| G10 | New accounts start with all four volume varps at 0 (the audio tab shows every channel muted). The source for the default of a fresh OSRS account is not known. **OPEN-G10:** left at 0. | rev 242 client |
